## 1 记录原则

本文件记录**做了什么、实际结果是什么、依据在哪里、接下来做什么**。开发日志不等于软件运行日志，后者由应用按统一规范第16章输出。

1. 每次开始任务登记目标、负责人、需求编号和准备修改的文件；当天结束、合并或交接前补齐实际结果。
2. 历史记录按编号追加，不抹掉失败和被替代决定。填错时追加更正，写清更正哪个字段和原因。
3. 状态固定为计划、进行中、已实现待验证、验证通过、受阻、已取消。交接的接收状态另外记录，不混用。
4. “预期结果”和“实际结果”分开；没运行就写未执行。文档、界面设计、假响应和真实软件实现分开。
5. 结果优先提供提交号、命令、退出码、测试数量、样例编号和证据相对路径。不要只写“正常”“没问题”。
6. 工时据实记录；没有记时就写未记录，不补造分钟数和完成百分比。
7. 不写Key、Token、Authorization、私人正文、带凭据的URL或用户完整路径。证据引用受控虚构样例，截图先脱敏。
8. 每人写自己的工作和复核，不把别人或AI完成的内容写成个人独立实现。AI协助单独注明，负责人仍承担审核责任。
9. 一条事实放一个主位置，其他地方引用编号。当前未完成总览放交接文档，历史过程放本日志。
10. 本文件中的“待填写”和示例是模板，不是项目已经发生的事件。

## 7 集成与测试记录模板

### INT-YYYYMMDD-待编号 验证范围

| 字段 | 记录 |
|---|---|
| 执行者、日期 | 待填写 |
| 被测版本与完整提交 | 待填写 |
| 环境 | 系统、CPU/内存、Kit、Debug或Release |
| 测试范围 | 需求编号与不包含的内容 |
| 数据与样例 | fixtures编号、节点数、输入类别 |
| 实际命令 | 逐条写真实命令 |
| 自动测试数量 | 发现数、执行数、通过数、失败数、跳过数 |
| 手工流程 | 点击输入步骤与结果 |
| 总结 | 通过 / 失败 / 部分通过 / 未执行，不能混称全通过 |
| 失败与限制 | BUG编号、原因和未执行项 |
| 证据 | 脱敏日志、截图、报告相对路径 |
| 复核人 | 待填写 |

不同类型的证据要分开：

- **离线验证**：记录确实断网、执行的四项特色及结果；仅没有点击AI不能算断网验证。
- **真实AI**：记录材料编号、用途、模型标识、提示模板版本、调用日期、耗时、token、结构合法、内容忠实、采用后编辑情况；不记录Key或私人原文。API返回usage缺失时写未提供，不估造费用。
- **部署**：记录目标电脑未安装开发工具、系统与版本、包的SHA-256、启动、文件、导出、TLS结果；不能仅在开发者电脑启动exe。
- **性能**：记录样例规模、测量起止、三次结果、中位数和最慢值；区分目标与已测数据。
- **文档**：记录格式、链接、配置示例与一致性；不与应用测试混淆。
