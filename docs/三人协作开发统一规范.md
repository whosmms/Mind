# 灵芽思维三人协作开发统一规范

版本：1.0  
制定日期：2026年10月24日  
适用范围：C++17、Qt 6、Windows 64位课程项目，三名开发者及协助开发的 AI。  
文件性质：开发约定与执行标准。文中的配置片段和命令供后续实施使用，不表示已经安装工具、建立源码工程、编译成功或完成 API 联调。

## 0 怎样使用本规范

三个人先共同阅读第1至6章，再按自己的模块阅读后续章节。开始编码前必须完成第4章的共同准备。每次提交、交接和发布分别按第18、21、23章检查。

配套文件：

- [三人开发交接文档](交接文档.md)：当前可交接状态、模块交接表、接收验证步骤及交接模板。
- [三人开发日志](开发日志.md)：开发日志、接口变更、缺陷、集成、发布和实际验证的记录格式。
- [软件设计与实施规范 AI版](设计与实施规范_AI版.md)：课程需求、完整领域字段、业务规则和功能验收的依据。
- 逐步开发操作手册（位于资料根目录，未纳入docs）：从环境准备到实现、测试与打包的操作说明。

约束用词：**必须**表示合并和验收的必要条件；**禁止**表示不能采用；**可以**表示在已明确的边界内自行决定。

### 0.1 文件之间的分工与优先关系

1. 用户的最新明确指示优先；执行者同时遵守适用的项目内 AGENTS.md。
2. 本文件确定三人协作、所有权、代码风格、变更、交接、日志和发布规则；旧设计中“两人方案”和“可以另选工具链”的建议不作为本团队默认方案。
3. AI版设计规范第1、4、5、6、7、8、10、11、15章仍是需求编号、JSON字段、业务边界、接口及验收的依据。本文件不另造第二份领域模型。
4. 日志只报告事实，不能凭一条“已完成”记录改变设计要求。交接文档描述已交付内容，不能把计划写成实现。
5. 发现规则冲突时先保留最后可用版本，在“接口与决策变更记录”登记冲突位置、采用方案、受影响文件及复核人，更新有关文档后再合并。普通实现选择由模块维护人和复核人解决，不逐项等待用户决定。

### 0.2 规则已经确定与现场事实尚待登记的区别

本文件已经确定版本锁定方法、模块负责人代号、目录、命名、错误处理、接口变更、分支、测试、交接、日志等规则。成员真实姓名、仓库地址、安装后的完整版本号、真实提交号和运行结果必须据实登记，不能为了填满表格而编造。

这些事实由指定负责人在 M0 填入交接文档。登记未完成时不进入多人分别编码；不允许三个人各自选一套版本后再补表。

## 1 已确定的项目决策

| 项目 | 统一决定 | 改动条件 |
|---|---|---|
| 首版平台 | Windows 10/11，x86_64；实际测试写明系统版本 | 跨平台需求作为后续正式变更 |
| 编程语言 | C++17，禁止要求 C++20/23 的代码 | 三人共同评估并记录升级 |
| 桌面框架 | Qt 6、Qt Widgets、Graphics View | 首版不引入第二套界面框架 |
| 开发环境 | Qt Creator，同一官方 Qt Kit | 依第5章统一锁定 |
| 编译器 | Qt 官方配套 MinGW 64位 | 不允许成员自行切换到 MSVC |
| 构建 | CMake + Ninja，Debug/Release 分目录 | 乙维护构建配置 |
| 单元测试 | Qt Test + CTest | 不同时引入另一套测试框架 |
| 数据保存 | `.lingya`，UTF-8 JSON，schemaVersion=1 | 文件格式改动必须走迁移评审 |
| 状态管理 | 唯一 ProjectDocument；统一 CommandService 与 QUndoStack | 页面不各存一份真实工程 |
| 网络 | Qt Network 异步 HTTPS，DeepSeek 官方接口 | 供应商变更需用户明确同意 |
| 密钥 | 默认仅会话；主动记住时用 Windows 凭据管理器 | 禁止明文文件或安装包内置共享密钥 |
| 分发 | 动态链接，windeployqt 收集依赖，Inno Setup 安装包 | 免安装版必须包含完整部署目录 |
| 源码协作 | 一个 Git 仓库、一个 main 分支、短功能分支、评审后合并 | 禁止互传整份源码覆盖 |
| 界面语言 | 中文 | API字段、标识符和工具名称保留合法英文 |
| 特色优先级 | 四项离线特色先完成，再做两项 DeepSeek 功能 | 不得用 AI 展示代替课程要求 |
| 不纳入首版 | 账号系统、云同步、实时多人协同、任意 Word/PDF 导入、自训模型 | 不得在个人分支自行扩张范围 |

选择这些约定可以减少初学者同时学习多套工具的成本，代价是必须遵守共同数据、生命周期和构建规则。首版以能保存、能继续编辑、能复现验证为先；复杂动画和装饰的优先级低于完整功能。

### 2.1 工作量和职责边界

乙的基础模块是甲、丙的依赖，应首先做最小可用接口，不等完整布局全部完成才给别人接入。丙的真实 AI 开发在 M5，前期优先协助数据规则、任务和测试，不能一直等待 API 阶段。

甲负责页面布局与交互规范；丙拥有任务、复习和 AI 页面的业务逻辑与对应功能代码。涉及这些页面的视觉调整由甲提出，丙提交或协调修改，避免两人同时覆盖一个文件。

### 2.3 共享文件的修改顺序

1. 在日志登记准备修改的共享文件、字段或函数、消费者及目的。
2. 维护人确认时间和边界；两个相关任务不要同时重写同一段。
3. 先提交头文件、示例和必要兼容处理，再接调用端。
4. 维护人与至少一名消费者复核；Domain、文件格式和公共服务的破坏性变更三人全部确认。
5. 记录合并提交与版本影响，通知调用者更新。聊天通知不能代替提交中的接口说明。

## 5 开发环境和版本锁定

### 5.1 安装基线

1. Qt采用6.8稳定系列及其官方配套MinGW 64位Kit作为首版基线。Qt 6.8官方Windows说明列出的MinGW基线为13.1；具体补丁和配套包以实际安装并验证的同一套为准。[Qt官方Windows支持说明](https://doc.qt.io/qt-6.8/windows.html)
2. Qt模块仅启用Core、Gui、Widgets、Network、Svg、Concurrent、Test；增加模块先登记目的、许可证和部署影响。
3. CMake项目最低版本3.21；实际所选Qt若要求更高，以更高者为准，并同步修改构建声明。
4. 格式化统一使用clang-format 19.1.7及第9章配置。它只格式化代码，不替换MinGW作为编译器。若该版本无法取得，乙提出全队一次性替换，不能三人各用不同主版本格式化。
5. Qt Creator、Git、CMake、Ninja和调试器也记录完整版本。工具必须来自官方或可核对的发行来源，不安装来路不明的“绿色整合包”。

Qt补丁号和安装路径不是凭文档推测的事实。乙先完成一套可用组合，再把完整版本和来源登记为**唯一环境基线**；甲丙复现后冻结。未冻结前不得各自大规模开发。Qt6.8系列实际可用组件不足时，乙可以在现有设计允许的Qt6稳定系列内组织一次全队迁移，须先验证三机和最小部署，不允许单人升级。

### 5.2 环境清单

环境记录必须包含：Windows版本与架构、Qt完整版本、Kit名称、MinGW和g++完整版本、Qt Creator版本、CMake版本、Ninja版本、Git版本、clang-format版本、安装来源、TLS后端、最后验证日期、验证提交和三人结果。

个人绝对路径只记录在个人环境段或不提交的 `CMakeUserPresets.json`；共享 `CMakeLists.txt` 不出现某人的 `C:/Qt/...`、用户名或桌面路径。应用根目录可以不同，工程内引用必须相对路径。

**禁止直接使用PATH上碰巧先找到的Anaconda、MSYS2或其他软件附带工具作为团队工具链。**先确认路径和版本属于登记的Kit。

### 5.3 通用构建预设

未来在 `app/CMakePresets.json` 使用以下起步配置。执行者先设置本机 `QT_KIT_DIR` 为已登记的Qt套件目录，并在已配置配套MinGW、CMake和Ninja的终端运行。此环境变量不含密钥。

```json
{
  "version": 3,
  "cmakeMinimumRequired": { "major": 3, "minor": 21, "patch": 0 },
  "configurePresets": [
    {
      "name": "base",
      "hidden": true,
      "generator": "Ninja",
      "binaryDir": "${sourceDir}/build/${presetName}",
      "cacheVariables": {
```

## 7 模块依赖、所有权和线程

### 7.1 固定调用方向

```text
用户操作
  → 页面或图元发出意图
  → EditorController或对应功能控制器
  → CommandService和校验器
  → 唯一ProjectDocument
  → changed信号
  → SceneAdapter、大纲、任务表等读取并刷新

AI面板 → AiService → IAiProvider/DeepSeekClient → Qt Network
                                              ↓
                        校验后的提案 → 预览 → 命令层采用
```

领域层不依赖页面、图元、网络和磁盘路径。布局只接收数据和测量结果。服务不直接改窗口。图元不直接保存文件或发送AI请求。

核心库 `lingya_core` 只包含不依赖界面的领域、序列化和纯规则代码，按需要链接Qt Core。QUndoStack属于Qt Gui，命令历史和文档服务放应用支持层，不为了测试把QWidget塞入核心库。应用支持层可组织为 `lingya_appcore`；窗口和场景放可执行目标，避免目标之间循环依赖。

### 7.2 对象生命周期

- QObject以明确父对象管理，或由明确的唯一所有者管理；不能同时交给父对象和独占智能指针销毁。
- 普通独占C++对象用 `std::unique_ptr`；领域结构按值存储。不为方便到处使用shared_ptr。
- SceneAdapter管理场景映射；图元加入场景后按场景所有权规则销毁，删除后立即清除ID映射。
- QUndoCommand只保存稳定ID和数据快照，不存NodeItem等可能失效的地址。
- 信号连接使用新式函数指针；lambda捕获QObject时提供上下文，异步完成前不能依赖已销毁的裸对象。
- 可以对QObject派生对象使用QPointer；普通QGraphicsItem不能直接用QPointer。

### 7.3 线程规则

GUI、QGraphicsScene、图元和控件只在GUI线程访问。QNetworkAccessManager采用异步请求，首版放GUI线程，不用阻塞等待或嵌套事件循环。

耗时布局与检查可使用QtConcurrent，输入为值副本；结果携带工程ID、会话ID和sessionRevision。回GUI线程核对三者后再应用；任何不一致均丢弃，不把过期结果覆盖到新工程。

同一工程的保存操作串行；文件对话框在GUI线程。后台只处理已取得的路径和数据，不弹窗口。关闭窗口要取消或安全忽略未完成任务，不能让回调访问已释放对象。

## 10 统一接口与错误处理

### 10.1 接口唯一来源

- 领域类型以 `Domain.h` 为准，AI类型以 `AiTypes.h` 为准；页面不得复制一份“简化版”后长期维护。
- 公开头文件是调用契约。新接口必须说明参数单位、是否可空、边界、返回值、失败和线程。
- 不返回指向局部变量的引用；不暴露Project可写引用；读取用只读视图或值快照。
- 日期用QDate，时间戳用UTC QDateTime，百分比是0至100整数，文件大小以字节计算，界面显示MiB。不要混用秒与毫秒、日期与时间戳。
- 新增字段默认值必须明确；缺省、null和空字符串按原JSON映射区分。
- 公开签名变更必须同时更新调用者、序列化、测试、fixtures与交接，不允许“头文件先合了，别人编译再说”。

### 10.2 返回与取消

常规可预期失败使用已有 `AppError { code, message }`，返回 `std::variant<成功类型, AppError>`。无业务返回值的成功类型使用std::monostate。AI保持AiError，不重复定义不兼容的错误结构。

文件选择取消由控制器处理，不伪装为保存失败。AI取消使用已有canceled信号，不能既发送canceled又发送failed。按钮禁用与错误提示由状态决定，不从提示文案反推状态。

所有界面提示为中文；错误code为稳定英文标识。禁止直接向用户展示堆栈、网络响应原文、Authorization或带个人路径的调试信息。

### 10.3 基础错误码补充

AI继续使用原规范已列出的错误码，不改名。非AI模块统一采用下表；新增错误须登记，不凭个人习惯造同义词。

| 错误码 | 含义 | 处理 |
|---|---|---|
| `INVALID_ARGUMENT` | 参数类型或必填值错误 | 不修改工程，定位输入 |
| `NOT_FOUND` | 节点、工作表或任务已不存在 | 刷新选择并说明对象失效 |
| `CONFLICT` | 版本或当前内容与操作依据不一致 | 重新读取或让用户选择 |
| `LIMIT_EXCEEDED` | 超过工程或导出限制 | 提示拆分或降低范围 |
| `INVALID_DATE` | 非法日期或时间顺序 | 保留原值，提示修正 |
| `DEPENDENCY_CYCLE` | 任务依赖成环 | 拒绝本次修改 |
| `INVALID_PROJECT` | 工程结构或引用错误 | 不替换当前工程 |
| `UNSUPPORTED_SCHEMA` | 文件版本不支持 | 保留当前工程，提示版本 |
| `FILE_NOT_FOUND` | 文件不存在 | 允许另选，最近记录可移除 |
| `FILE_READ_FAILED` | 文件读取失败 | 原工程保持不变 |
| `FILE_WRITE_FAILED` | 写入或提交失败 | 保持dirty和内存内容 |
| `BACKUP_FAILED` | 旧文件备份失败 | 另存或取消，不冒险覆盖 |
| `EXTERNAL_MODIFICATION` | 文件被外部修改 | 另存或明确重新载入 |
| `EXPORT_FAILED` | 渲染或导出写入失败 | 不损坏原工程 |
| `INTERNAL_ERROR` | 未预期的内部问题 | 安全终止本操作并记录脱敏事件 |

assert只用于开发期内部假设，不能代替对外部文件和网络的校验。异常不能穿过Qt事件回调边界而无人处理；不通过catch-all把任何问题转换成“成功”。

### 11.3 读写与恢复

- 加载先检查大小和格式，再建立临时Project，完成字段、类型、引用和业务校验后才替换当前工程。
- schemaVersion仍为1。拒绝未来版本；改持久化语义必须设计迁移、旧样例和往返测试，不悄悄改变同名字段的含义。
- 保存先备份现有文件，不移动或删除唯一原件；使用QSaveFile，关闭直接写入回退，检查write长度和commit。
- 保存成功且保存期间没有新编辑，才setClean；失败保留dirty。保存后台拿的是固定快照，不能因旧快照成功而标记新修改已保存。

- 恢复快照与正式保存是不同状态。只清理应用自己创建的快照，不能把用户的正式文件当缓存删除。
- 新建未命名工程也有恢复能力；启动发现快照先预览，由用户决定采用。

## 12 命令、历史与一致性

所有持久化修改经过CommandService：在候选值上修改→校验→创建before/after快照命令→push一次。QUndoStack::push会执行首次redo，禁止预先修改原文档后再push。[Qt撤销栈说明](https://doc.qt.io/qt-6.8/qundostack.html)

文字编辑结束为一条历史，拖动松开为一条历史，AI一次采用为一条历史。选择、缩放、悬浮和讲解计时不进入工程内容历史。

删除、剪切、任务联动、AI采用必须把相关节点、任务、关系、注释等作为同一事务处理。失败不压栈，撤销完整恢复，不只恢复画面。

sessionRevision每次编辑、撤销、重做和工程替换均递增，不能随undo退回；Project持久化revision按规范更新，异步校验同时使用会话标识，避免两个工程版本号碰巧相同。

历史达到内存预算按原规范提示并清空旧历史后继续新操作，保留当前内容；不能承诺任何工程永远保留50步。文件写盘不放入QUndoCommand，撤销不重复读写磁盘。

## 13 图形、布局和任务规则

- 节点尺寸由统一字体、最大宽度和文字测量得到；测量与绘制必须相同。几何变化前prepareGeometryChange，边界含边框与徽标。
- 甲提供节点尺寸映射，乙提供稳定ID到位置的布局结果。布局结果不反向改标题或任务。
- 树按可见子树实际高度均衡布局；鱼骨复用树数据；流程图使用有向图模型，环先分组再布局，不丢边、不当树处理。
- 自动布局必须确定性：同样输入和参数得到同样结果；相同优先级用order、稳定ID打破平局，不依赖QMap以外容器的偶然遍历顺序。
- 任务表与甘特时间轴读同一Task；日期计算用QDate的daysTo/addDays。跨月、闰日、跨年有测试。
- 拖动预览不连续生成大量持久化修改；松开校验后提交一次。依赖首版只支持FS，后继开始日必须晚于前驱结束日。
- 连线、批注、外框和概要按各自数据模型处理，禁止用一张不可编辑图片冒充选做功能。
- 布局和图形调试日志不输出节点文字或完整工程。

## 15 DeepSeek与密钥规范

### 15.1 接口边界

使用官方 `https://api.deepseek.com/chat/completions`，Qt Network发送JSON。2026年10月24日核对官方入门页，默认模型标识仍为 `deepseek-flash`；可选模型列表集中配置，正式联调前再次核对，不把模型名当永久不变常量。[DeepSeek官方入门](https://api-docs.deepseek.com/zh-cn/)

非思考、非流式、JSON对象模式沿用原规范；具体参数须以联调时官方接口支持为准。禁止另接工具执行、网页搜索、任意URL、文件操作或脚本能力。

AiPanel只调用AiService；AiService控制业务、上下文、校验和预览；Provider只处理HTTP、受限重试和脱敏错误。FakeAiProvider只用于测试和明确标识的开发演示，不算真实API完成。

### 15.2 请求生命周期

每个请求必须有requestId、工程/会话标识和源版本。窗口同一时刻最多一个生成请求；忙碌返回BUSY。AI默认不自动读取所有工作表，只发送用户本次选择的输入或分支。

执行顺序：本地输入校验→请求→HTTP状态和传输结果→完成原因→非空内容→JSON→业务结构与来源校验→预览→采用前复核源版本→统一命令写入。

只接受完整合法内容，不自动修补截断JSON后假装成功。预览不自动污染原工程；取消、失败、超时或源变化均保留原内容和用户输入。每个请求只发一个终态。

单次90秒、总预算180秒、最多2次网络请求；仅明确允许的可重试响应自动重试一次。已发送后超时或中断可能已经计费，默认由用户主动重试。禁止嵌套重试、无限轮询和启动时自动测试连接。

### 15.3 凭据与隐私

- 不在源码、README、提示模板、JSON、截图、日志、交接、环境变量示例或安装包中写真实Key。
- 默认仅保存在本次会话；主动记住时封装Windows凭据管理器。QSettings只存非敏感配置。
- Key输入框用密码模式，设置成功后清空；状态接口只返回是否配置，不回传Key。
- 固定官方域名，拒绝重定向，保持TLS证书验证，不调用ignoreSslErrors。
- UI在生成入口清楚说明将发送所选材料，并由用户点击生成；不在后台隐式上传。
- 日志不记录请求/响应正文、Authorization、完整URL查询、节点文字或用户文件路径。
- 泄露时先撤销该Key，再处理仓库和记录；只删除当前文件的一行不足以清除Git历史。事故日志只写处置状态，不抄录泄露值。

## 16 日志体系与记录边界

“日志”分为开发过程记录和软件运行日志，两者不能混在一个文件中。

### 16.1 开发记录

由配套《三人开发日志》定义六类记录：每日开发、接口与决策、缺陷、集成与测试、发布、异常处置。开始编码前登记本次目标与文件；一天结束或交接前补充真实结果、提交、验证和下一步。

状态只用：计划、进行中、已实现待验证、验证通过、受阻、已取消。模块交接另外使用“待交接/待接收验证/已接收/退回”。没有实际执行就写“未执行”，不把预期结果填进实际结果。

### 16.2 运行日志

后续建立统一日志入口，采用Qt分类日志和统一消息处理器，严禁散落任意qDebug输出。运行日志写到 `QStandardPaths::AppLocalDataLocation/logs`，格式JSON Lines，每行一个事件，UTF-8。

固定字段：`timestampUtc`、`level`、`category`、`event`、`appVersion`、`sessionId`、`requestId`、`errorCode`、`durationMs`、`message`。无对应值时requestId、errorCode、durationMs写null；message为脱敏中文短句。网络日志不额外加入body字段。

```json
{
  "timestampUtc": "2026-10-24T00:00:00.000Z",
  "level": "warning",
  "category": "file",
  "event": "save_failed",
  "appVersion": "0.1.0",
  "sessionId": "example-session",
  "requestId": null,
  "errorCode": "FILE_WRITE_FAILED",
  "durationMs": 18,
  "message": "保存失败，原文件和当前编辑内容已保留"
}
```

该样例为格式演示，不是一次真实运行记录。

level仅debug/info/warning/error；category仅app/document/command/file/layout/ui/ai/recovery/deployment。默认Release记录info及以上，Debug可启用debug。INFO只记启动版本、操作类型和完成状态，不记录用户正文。

单日志最大5 MiB，当前文件加两份轮换归档总计最多约15 MiB；打开新日志时检查并清理7天前的本应用日志。仅操作专用logs目录中本应用命名的文件，不递归清理用户目录。写日志失败不阻止编辑或形成递归错误日志；退出时尽量flush。日志导出为用户主动动作，导出前仍检查脱敏。

乙维护统一入口和轮换，丙复核网络脱敏，甲复核错误提示。运行日志不是测试报告，也不自动证明功能正确。

## 17 Git分支、提交与冲突处理

### 17.1 仓库与分支

采用一个私有远程Git仓库；默认Gitee，若团队已有可用Git托管仓库则沿用，规则相同。乙负责记录无密钥仓库地址、权限和保护设置，禁止在地址中嵌入Token。此约定不代表已经创建远程仓库。

main为唯一集成分支，必须保护：禁止强推、禁止删除、禁止直接合入未评审代码；至少一名非作者通过并完成要求的检查。平台不能强制设置时，仍按相同步骤执行并留记录。

功能分支使用 `feature/a/R01-node-edit`、`fix/b/BUG-001-save-state`、`docs/c/DOC-001-test-plan` 等；a/b/c对应甲乙丙，编号取需求或记录编号。分支一次只解决一个可验收目标，原则上一至三天内集成，长任务拆小闭环。

集成采用普通合并保留提交记录；禁止对已共享分支rebase/force-push。main合并由乙操作；乙是作者时由甲操作且丙评审，不能乙给自己批准。Git合并和冲突的含义见[Git官方说明](https://git-scm.com/docs/git-merge)。

### 17.2 提交信息

格式为 `类型(模块): 中文动作说明 [编号]`。类型固定feat/fix/refactor/test/docs/build/chore；模块使用domain/editor/storage/layout/chart/review/presentation/check/ai/ui/package等已有目录语义。

```text
feat(editor): 支持新增子主题并加入撤销历史 [R01]
fix(storage): 保存失败时保留未保存状态 [S01]
test(chart): 补充闰日和跨月排期用例 [R13]
docs(handover): 补充基础编辑模块接收步骤 [H-001]
```

正文写修改原因、对外影响、实际检查及未完成部分。禁止只写“更新”“终于好了”“最终版”。一次提交不混入无关大重命名或格式清理。

### 17.3 日常操作顺序

下面是实施时的命令示意，必须在真实仓库中执行；本次文档制作不会替三人提交或推送。

```powershell
git switch main
git pull --ff-only
git switch -c feature/a/R01-node-edit
# 编码并完成验证后，先检查具体差异。
git status --short
git diff --check
git diff
# 逐个添加本次文件，禁止未检查就添加整个工作区。
git add src/graphics/NodeItem.h src/graphics/NodeItem.cpp
git diff --cached
git commit -m 'feat(editor): 支持主题编辑交互 [R01]'
# 接口或main有更新时，在功能分支合入main并再次检查。
git fetch origin
git merge origin/main
git push -u origin feature/a/R01-node-edit
```

上述源路径需按实际变更替换；命令只是流程模板，不能把未改动的文件名机械照抄。远程合并请求由开发者在仓库平台创建，按第18章填内容。

有未提交工作时先形成明确的本地提交或个人备份，再切分支；禁止用reset --hard、clean -fd或强推来“快速解决”他人的改动。

### 17.4 冲突与回退

冲突由产生冲突的两位成员共同理解后逐段解决，禁止整文件全部选“我的”或“对方的”。解决后跑受影响测试和完整构建。

已合并问题优先新提交修复，必要时用revert产生可追踪回退提交；回退合并提交由集成负责人核对父提交后执行，不提供不加判断的一键回退。运行记录写明影响、回退或修复提交及复验。

## 18 合并请求与代码评审

每次合并请求必须包含：

1. 需求或缺陷编号、原问题、完成后的真实行为。
2. 修改文件、模块和共享接口影响；是否影响JSON/旧样例/依赖/密钥/部署。
3. 实际构建和测试命令、运行结果、验证提交；未执行项明确写原因。
4. 真实界面变更的截图或短录像，不能用设计图充当实现截图。
5. 已知问题、限制、回退方案及对应交接编号。
6. 作者与复核人。共享契约按第2.3节加相关消费者。

评审逐项检查：

- 是否覆盖目标需求、无擅自删项或扩张。
- 是否遵守唯一数据和命令事务，是否可保存、撤销、重开。
- 是否有空值、长中文、无效引用、错误输入和生命周期问题。
- 是否正确处理GUI线程、异步版本与取消。
- 是否包含不必要依赖、真实密钥、用户材料或个人路径。
- 是否提供有意义测试和可复现步骤；没有零测试假通过。
- 是否与同一提交的接口、文档和示例一致。

超过约500行实质逻辑变化时优先拆分；M0骨架、自动生成文件或fixtures批量增加可说明原因，不能因此省略评审。评审发现阻断问题必须修复或明确缩小本次范围后再合并，不能合并后把必做项改成永久TODO。

## 19 测试、构建与阶段验收

### 19.1 测试责任

每个模块编写者提供测试，默认复核人复现，丙维护全量清单。测试关注规则、边界和曾经出错的行为，不机械复制实现。

| 范围 | 必测内容 | 证据 |

临时文件测试使用QTemporaryDir，禁止操作个人文档作为测试数据；异常磁盘条件优先使用可注入失败的文件服务和受控临时路径，不破坏真实磁盘。

### 19.2 合并前最低检查

在已冻结工具链终端、源码根目录执行：

```powershell
git diff --check
cmake --preset debug
cmake --build --preset debug --parallel 2
ctest --test-dir build/debug -N
ctest --preset debug --no-tests=error
```

要求：配置和构建返回0、无新增警告、测试数量不为0、全部应执行测试通过。首次纯空窗口搭建尚未建测试时只能记“环境启动验证”，不能记“M0全部通过”；M0验收前必须建立测试。

合并前对变更的.h/.cpp使用锁定版本 `clang-format --dry-run --Werror` 检查，或者先 `-i` 格式化再核对差异。不要无差别格式化别人的模块。

每个里程碑再执行Release构建和测试；Qt UI自动测试可以在隔离任务中使用offscreen平台，但不能以此代替真实Windows显示、输入法和安装包检查。

CI条件允许时由乙配置Windows构建和CTest，日志保持脱敏。CI尚未接通期间由非作者在另一台电脑对相同提交执行，不把“准备配置CI”写成已运行。

### 19.3 完成标准

一个任务只有同时满足以下条件才为验证通过：真实功能接入完整程序；成功和失败路径均处理；持久化内容能保存重开；应支持撤销的操作可撤销；对应测试和交互复查通过；界面及数据不含假状态；文档、日志、交接与代码一致。

AI真实调用、干净机器部署、性能测量分别验收。没有这些证据就分别标“待联调”“待部署验证”“待测量”，不能用单元测试代替。

性能目标沿用原设计：300节点打开到可编辑≤3秒，常规编辑反馈通常≤100毫秒，自动布局≤1秒。必须记录硬件、系统、构建类型、样例、测量方法、三次结果、中位数与最慢值，不提前填写达标。

## 20 缺陷、范围与决策管理

缺陷严重度固定如下：

| 等级 | 定义 | 合并与发布要求 |
|---|---|---|
| P0 | 密钥泄露、可重复数据丢失、破坏用户文件 | 立即停止有关发布，优先处置；未复验不得发布 |
| P1 | 课程核心流程不可用、稳定崩溃、保存重开错误 | 阻断对应阶段和最终发布 |
| P2 | 有替代操作的局部功能或明显显示问题 | 记录负责人和计划；属于必做验收仍须修复 |
| P3 | 文案、轻微视觉或非必需优化 | 可有理由延后，列入已知限制 |

“低严重度”不等于可以删掉已承诺功能。需求编号R01至R13、X01至X06、S01/S02始终追踪。

决策分类：实现细节由维护人与复核人决定；接口与共享格式按第2.3节；供应商、付费依赖、云上传、公开发布和课程范围改变涉及用户既定约束时取得明确指示。不得为每个局部函数写法增加审批。

决定必须写问题、备选方案、取舍、结论、负责人、复核人、日期、影响和回退。不能在日志写“讨论通过”而不写具体采用什么。

## 21 交接规则

交接不只是发压缩包。配套交接文档必须让另一人从指定提交开始，独立构建、运行目标流程，并准确知道还缺什么。

### 21.1 需要交接的时机

- 一个可集成模块完成，交给调用者连接。
- 公开接口、文件格式、工具链或资源规则改变。
- 阶段M0至M6结束或准备发布。
- 某人离开任务、交换角色、需要另一人接手。
- 新的AI会话接手编码或排错。

### 21.2 必须提供的内容

每条交接包含交接编号、角色与姓名、接收人、任务编号、分支、完整提交号、干净状态、环境、文件清单、职责边界、接口、启动与测试命令、结果、样例、已知问题、未完成项、下一步、回退和证据链接。日志/截图必须脱敏。

最终交接以已提交并可取得的代码为准。紧急交接如果工作区未提交，只能标“临时草稿交接”，附明确文件和补丁；不能冒充可复现正式交付。

### 21.3 接收流程

1. 交付者自测并填写交接文档，状态为待接收验证。
2. 接收者获取指定提交，核对版本和工作区，不覆盖自己的未提交工作。
3. 按交接命令构建，执行成功、失败、保存重开、撤销和目标模块演示。
4. 记录自己实际执行的结果。缺源码、命令不对、关键测试缺失或未完成功能被标完成时退回，列具体原因。
5. 接收通过后填写接收人、日期、验证提交和遗留项；需要修复时新建缺陷，不擦掉原交接记录。

交付者和接收者必须是不同人。约定下一个共同工作时段完成接收，无法及时验证时保持待验证；经过一天或两天不自动视为接受。

## 22 文档、日志和贡献记录

- README：安装基线、构建运行、测试、配置入口和常见问题；新成员从这里开始。
- environment：同一套工具链的事实和三机复现，不放Key。
- decisions：已采用的技术和接口变更，注明被替代记录。
- acceptance：需求、阶段、结果、提交与证据，状态可追溯。
- 交接文档：当前交接状态与接收记录，按编号保留历史。
- 开发日志：按记录编号追加事实，覆盖开发、缺陷、集成、接口和发布。
- third-party：组件、版本、来源、授权、用途和需要随包提供的文件。

一项事实有一个主记录位置；其他文档引用编号或相对链接，不复制大量容易漂移的状态表。默认“当前状态”以总交接为入口，历史以日志为依据，实际代码以提交为依据。

日志不记“做了一整天所以完成度80%”等无法核查百分比。记录具体操作、输出、失败、判断和下一步。个人贡献依据提交、设计和复查证据，三人都能解释共同模块与自己的工作。

所有Markdown必须有标题、日期或版本、适用范围；标题层级连续；本地链接有效；示例、计划、真实记录明确分开。文档改动和代码改动使用同一合并请求，不能长期保留只在聊天中的关键规则。

## 23 版本、部署和发布

### 23.1 版本规则

应用版本使用0.x.y：M0起0.1.0；阶段或对用户可见能力增加提升次版本，兼容修复提升修订版本；最终课程验收后发布1.0.0。Git标签如 `v0.1.0`、`v1.0.0`，只能指向已验收提交，不移动旧标签掩盖问题。

schemaVersion与应用版本独立，不能应用版本加一就随意改变文件结构。发布清单写应用版本、完整提交、构建工具链、Windows测试环境、日期、功能范围、已知问题和SHA-256。

### 23.2 固定发布流程

1. 乙从干净源码取得指定main提交，先跑Debug和Release检查。
2. 放程序到独立staging目录，用同一Kit的windeployqt收集依赖；补充经验证的TLS、SVG等插件和所需运行库。
3. 甲在另一台未安装Qt的Windows电脑或干净虚拟机测试启动、编辑、中文、保存、重开、导出和资源。
4. 丙执行离线特色与AI真实联调检查，记录当前模型、请求类别、token、耗时、结果，禁止记录Key和原始私人材料。
5. 乙用Inno Setup封装 `LingyaMind-版本-win64-Setup.exe`；免安装版为整个部署目录ZIP，不仅一个裸exe。
6. 测试安装、覆盖升级、卸载；程序卸载默认保留用户工程，应用数据与凭据清理必须有明确选择。
7. 丙汇总需求验收、P0/P1缺陷清零和已知限制，甲复核实际演示，乙登记发布校验值后打标签。
8. 留存源码快照、部署包、安装包、运行说明、设计、测试报告、演示工程和第三方许可证。

安装器AppId保持稳定；升级规则、安装目录权限与用户数据目录分开。程序和自动恢复不写Program Files。临时测试包必须标明版本和未验收状态，不能与正式课程交付混名。

### 23.3 备份与可恢复性

Git只管理源码与受控资料，不能代替用户数据备份。每个里程碑保留代码标签和测试证据；远程仓库故障时可以从另一人完整克隆恢复。

禁止把build和下载缓存当源码备份。备份中不存共享Key；临时密钥由各使用者独立保管。发布文件损坏或内容不符时以校验值和对应提交重建，不猜测哪个“最终版”才是正确版本。

## 24 AI协助开发的统一要求

三个人可以使用AI，但必须使用同一套设计和接口，不把不同聊天生成的三个独立项目拼起来。交给AI时至少提供：本规范、AI版设计、当前阶段、当前代码路径、交接编号和目标任务。

AI开始前先读取AGENTS、当前结构、相关头文件和测试，说明将改文件。先实现一个可验收的小闭环，不一次生成几十个占位模块。

不得把真实密钥粘贴给AI或写入提示。AI输出由负责人审查并实际验证；不能仅凭AI说“通过”填写验收。未运行Qt、测试、API或安装包时必须标未执行。

可直接复制的任务模板：

```text
请在现有灵芽思维C++17/Qt6工程内完成一个小任务。
先阅读项目AGENTS.md、三人协作开发统一规范、AI版设计和当前交接记录。
角色：填写甲/乙/丙；目标需求：填写R/X/S编号；当前阶段：填写M0至M6。
代码目录：填写实际目录；基线提交：填写真实提交号。
本次目标：填写一个能够验证的流程。
先检查结构和相关接口，列出修改文件及原因，再动手。
遵守统一数据、命令、线程、错误、密钥、格式与测试规则。
不扩张需求，不创建另一套项目，不覆盖他人未提交改动。
完成后给出真实修改、运行命令、结果、未执行项及遗留问题，
更新对应开发日志与交接；没有证据不得声明功能已完成。
```

## 25 团队执行节奏

每天开始：同步main、查看交接和阻断、登记本日目标与共享文件占用。结束：提交可解释的修改、补实际日志、列下一步；无法完成时交出真实状态。

每周至少两次短集成，三人共同演示真实流程，检查新建保存重开、接口变化、跨模块一致性和当前缺陷。具体时段在M0按课程安排登记，之后固定执行。

每个阶段结束：按第3、19章验收，检查需求无遗漏、交接已接收、日志有证据，再进入下一阶段。工期不足先减少非必要装饰和超范围扩展，不自行删除老师选做项或已确认特色。
